# Phase 4 WP-4.2: Deployment Architecture

## Edge / Central Separation
NETRAKSH uses a strict Edge / Central deployment boundary. The Edge node handles camera ingestion, inference, Re-ID processing, evidence buffering, and offline queues. The Central platform handles persistence, object storage, unified correlation, API serving, and frontend hosting.

## Topology

### Edge Node (`docker-compose.edge.yml`)
- **edge (netraksh-edge)**: The physical camera-attached compute node. Connects outward to the Central Backend over an mTLS-secured tunnel. Disconnected operation is fully supported through a local persistent SQLite event queue (`/app/edge/data`).

### Central Platform (`docker-compose.yml`)
- **frontend (netraksh-frontend)**: The React dashboard, served via Nginx.
- **backend (netraksh-backend)**: The FastAPI service handling ingress from edge nodes and the frontend.
- **db (netraksh-db)**: PostgreSQL 15 database storing long-term unified correlation, cameras, identities, and metadata.
- **minio (netraksh-minio)**: S3-compatible object storage acting as the secure repository for binary evidence blobs.

## Data Persistence Strategy
- **Edge**: Ephemeral execution. The only persistent volume is `edge_data`, holding the offline sync queue and temporary evidence staging directory.
- **Central**: Persistent storage relies on `postgres_data` (for PostgreSQL metadata) and `minio_data` (for binary evidence objects).

## Separation of Concerns
1. The Edge node **must never** have direct access to Central PostgreSQL or MinIO.
2. The Edge node communicates exclusively with the Central FastAPI ingress via standard REST, signed with its `CameraKey`.
3. Object storage interactions (binary blob uploads/downloads) are brokered through signed S3 URLs generated by the Backend, not through direct Edge-to-S3 bucket credentials.
