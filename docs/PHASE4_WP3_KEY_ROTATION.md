# NETRAKSH — Phase 4 WP-3.1 Key Rotation & Revocation Policy

## Rotation Sequence
When an edge device replaces its Ed25519 keypair, the backend executes the following rotation safely:

1. **Key A is ACTIVE.**
2. Edge generates a new keypair and uploads it via `PUT /api/cameras/{id}/public-key`.
3. Backend derives `kid_B`.
4. Backend identifies all existing `ACTIVE` keys for this camera (Key A).
5. **Key B is registered and activated** (`status = ACTIVE`).
6. **Key A is RETIRED** (`status = RETIRED`, `retired_at` populated).
7. Future evidence packages generated by the edge append `kid_B` to their payload.
8. **Historical Evidence signed by Key A remains cryptographically verifiable.** 
   The Verifier (`verify_signature`) will successfully validate the Ed25519 signature of historical packages by looking up Key A using its `kid` or falling back to the legacy resolution flow.

### Immutable History
At no point is Key A deleted, overwritten, or automatically revoked merely because a new key was provisioned.

## Revocation Semantics
Revocation (`status = REVOKED`) is a strictly manual security action taken when a private key is known to be compromised or leaked. 

If a key is REVOKED:
- Evidence signed prior to the revocation remains **cryptographically valid** (the math holds up).
- However, the operational status of the evidence becomes inherently suspect.

To correctly model this, the API distinguishes between:
**A. Cryptographic Validity** -> `SIGNATURE: VALID`
**B. Operational Key Status** -> `(KEY: REVOKED)`

An auditor querying a historical evidence package signed by a revoked key will receive:
`SIGNATURE: VALID (KEY:REVOKED)`
This indicates that while the system can prove the evidence wasn't tampered with post-signing, the original signer (the key) is fundamentally compromised.
